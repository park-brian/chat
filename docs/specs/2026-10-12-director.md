# The harness as director

The user's direction (2026-10-12): the harness steers the model by injecting instructions at the right time, does
much of the work itself, enforces a checklist the model can verify (like a test suite), keeps plans and documents
current and keeps looking back at them, and gives the model goal-oriented behavior. Optimized for cheap models:
Haiku 5.5 and Gemini 3.8 Flash.

This builds on docs/specs/2026-10-12-harness-design.md (hypotheses checked against reality) and on what the evals
showed: a rule in the prompt ("write a plan file") changed nothing; the same rule injected by the harness after the
eighth call worked in 3 of 3 runs.

## How cheap models behave, and what follows

1. **The end of the context counts most.** Instructions just before the model acts are followed; rules 6k tokens
   up in a system prompt are followed unevenly. So: keep the system prompt stable and short, and put the
   instruction for *this* step at the tail of the request.
2. **They follow feedback better than rules.** A tool result that says "3 tests failed: …" changes the next action
   reliably; "always test your work" does not. So: turn rules into checks whose results arrive as feedback.
3. **They claim more than they did.** "17 passed" with no report. So: facts about progress come from the harness's
   records, not from the model.
4. **They stop early when they believe they are done**, and they keep going on a failing approach. So: the harness
   decides when an item is done (its check passes) and notices when the model is stuck.
5. **They lose the thread after a summary.** So: the durable state is outside the conversation, in files the
   harness owns, and the harness re-injects the parts that matter after every summary.
6. **They do one well-specified thing at a time better than many at once.** So: the harness hands over one item,
   with its check and the notes relevant to it, instead of the whole plan.
7. **Long, nuanced instructions cost them more than strong models.** So: injected instructions are one to three
   plain sentences that name the next concrete action.

The division of labor: **the model makes the judgments** (what the user means, how to build it, what a failure
says), and **the harness does the bookkeeping** (what the goal is, what is done, what was checked and how, what
was learned and from where, what to do next, when to stop).

## The generic pattern: a contract of checks

Every non-trivial task becomes a small contract:

```
Goal        the user's request in their words, and what done means
Assumptions what the agent decided without asking, each one correctable
Items       ordered steps; each has a check
Checks      executable tests of an item, run by the harness
Ledger      what was checked, when, with what result and evidence
Notes       facts learned, each with its source; decisions, each with its reason
Questions   what only the user can answer
```

The rules that make it work:

1. **Every item has a check, and checks are run by the harness.** An item is done when its check passes, not when
   the model says so. The model can propose and edit checks; it can't mark items done.
2. **Red first.** A new check is run once when it is added. A check that already passes before the work is not a
   check of the work, and the harness says so. This is test-driven development applied to any task, and it stops
   weak checks (a model gaming its own contract).
3. **Every passed check stays passed.** At each milestone the harness reruns all previously green checks; a
   regression reopens its item.
4. **Evidence is recorded by the harness.** The ledger keeps the check, its output, and the time. Final reports
   quote the ledger, and a claim in the final message that the ledger contradicts is flagged.
5. **Notes outlive context.** A fact learned is written to Notes with its source before the result that showed it
   is cleared. The harness re-injects Goal, the current item and the relevant Notes after every summary.

### Check kinds (so the pattern covers every kind of task)

| Kind | Example | Run by |
| --- | --- | --- |
| test | the app's in-file tests, a node:test file, a hidden suite in evals | the run report / code tool |
| probe | a script run in the artifact: `window.sheet.value("B1") === "8"` | run_app |
| file | a file exists, matches a schema, is under N words, contains a section | the workspace |
| source | a quote appears in fetched text; a number appears in tool output | the ledger of tool results |
| compute | a value recomputed by the harness from the recorded code | the code tool |
| consistency | a chapter agrees with the facts registry (names, dates, places) | a judge call with the registry |
| judge | one binary criterion by a separate model, as a last resort | a reviewer sub-agent |
| user | a question resolved by the user's answer | the user |

Domains map onto the same contract:

- **A Lisp compiler**: items by feature (reader, numbers, define, lambda, closures, tail calls, macros), each with a
  test file; the hidden suite in evals.
- **A game** (the No Man's Sky question): items by system (terrain, flight, inventory, scenes), each with a probe
  and a frame budget; the replay check for determinism.
- **A book**: items are chapters from an outline; checks are length, the facts registry (a JSON file of characters,
  places, dates, open threads) and a consistency judge per chapter against it, plus "every thread opened is
  closed" at the end.
- **Research**: items are questions or hypotheses; checks are source quotes and recomputed numbers; Notes hold
  each finding with its URL.
- **A plain question**: no contract. The director only acts on work past a size threshold.

## The director

A small state machine in the engine that reads the contract and the run's events, and decides what to inject.

### Phases

1. **Understand**: the agent states the goal in the user's words, its assumptions and what done means; it asks only
   what only the user knows. The harness shows assumptions to the user as correctable chips.
2. **Contract**: the agent writes items with checks. The harness runs each check (red first) and reports which are
   not real checks.
3. **Work**: one item at a time. At the start of each step the harness injects the current item, its check, and the
   Notes that mention its files or topic. After each change, the harness runs that item's check.
4. **Milestone**: when an item's check passes, the harness reruns earlier checks, records the ledger entry, and hands
   over the next item. Every few items, or at the end, a fresh-context reviewer compares the work with the Goal;
   its findings become items with checks.
5. **Close**: the harness assembles what passed, what failed and what was not verified; the model writes the
   message from that. Claims that contradict the ledger are flagged.

### Triggers and injections

Each rule is a condition on the contract and the event stream, an injection of one to three sentences, and a
frequency. The existing reminders (silent, failing, untested, unadopted, polished, unplanned) become rules in this
table.

| Condition | Injection |
| --- | --- |
| Work past the size threshold and no Goal yet | "Before more work, state the goal in the user's words, your assumptions, and what done means, with plan(goal)." |
| Goal set, no items | "List the steps with plan(add), each with a check the harness can run." |
| A check passes before any work | "This check already passes, so it can't show the item is done. Make it fail first." |
| An item's check passes | "Item 3 is done (check passed). Next: item 4, …; its check: …." |
| The same check fails twice the same way | "Item 4 failed twice with the same error. Read the code and the error again before the next edit, or split the item." |
| N steps with no check turning green | "No progress in 6 steps on item 4. Change approach, split it, or ask the user." |
| A summary just ran | "Goal: …. Done: items 1-3. Current: item 4, check: …. Notes: …." |
| Context near the budget | "Context is at 80%. Write what you learned to Notes now; old results are about to be cleared." |
| The model stops with items open | "Items 4 and 5 are open. Continue with item 4, or say why it should stop here." |
| The final message claims what the ledger doesn't show | "Your reply says the tests pass; the last run shows 2 failures. Correct the reply." |
| A question to the user is open and other items don't depend on it | "While the question is open, continue with item 5, which doesn't depend on it." |

Placement: every injection goes at the tail (appended to the tool results, or as a user message at a turn's end),
marked `harness`. The system prompt doesn't change during a run, so the cache prefix holds.

### What the harness does itself

- Runs checks after every change to the files an item names, and records the results.
- Writes ledger entries and the run's progress line ("4 of 9 items done, 31 checks green") into the request.
- Renders the contract as PLAN.md for the user (and the Goal and assumptions as an editable card in the UI).
- Re-injects Goal, current item and relevant Notes after summaries.
- Decides stop conditions: all checks green, a budget spent, or a question only the user can answer.

## How the model talks to the contract

A `plan` tool, with small operations:

```
plan({ goal: "...", done: "...", assumptions: ["..."] })
plan({ add: { title, check: { kind, ... } } })        one item; check optional only for kind "user"
plan({ note: "...", source: "url or path" })
plan({ ask: "..." })                                  a question only the user can answer
plan({ edit: n, ... })                                change an item or its check (the old check is kept in the ledger)
```

Items are never marked done by the model. The tool's result is always the current state in a few lines (goal,
counts, current item and check), so the model sees the contract every time it touches it.

PLAN.md stays: the harness writes it from the contract after each change, so the user and future sessions can
read it, and it survives across chats.

## For cheap models specifically

- **Shorter system prompt.** Move procedure (how to plan, test, verify) out of WORKING and into the director's
  injections, which arrive only when relevant. The system prompt keeps the persona, the writing rules, the tools
  and the environment.
- **One instruction at a time**, naming the next action.
- **Checks the harness can run without the model's help** wherever possible (test, probe, file, source), and a
  judge only where nothing else works.
- **No long-range memory required**: the next item and its context are handed over.
- **Measured on Haiku 5.5 and Gemini 3.8 Flash**, both as the worker; Sonnet 5.5 only as the judge and simulated
  user.

## Risks

- **Over-scaffolding.** A checklist on a short task wastes time and tokens, and current guidance warns that recipe-
  like instructions can hinder newer models. The director only starts past a size threshold, and every rule is
  measured by removing it.
- **Weak checks.** A model writes a check that is easy to pass. Red-first catches checks that pass without work;
  the reviewer reviews checks as well as work; evals keep hidden checks the model never sees.
- **Cost.** Running checks after every change costs time. Checks run only for the item's files, and the full set
  only at milestones.
- **Rigid plans.** Plans must change when the work teaches something. `plan({ edit })` is cheap, and the stall rule
  suggests splitting or changing an item.

## Build order

1. The `plan` tool, the contract store (per thread, in IndexedDB) and PLAN.md rendering. Checks of kinds test,
   probe, file and source, run by the harness, with red-first.
2. The director: phases and the trigger table, replacing the six ad-hoc reminders with rules. Re-injection after
   summaries. The progress line.
3. A shorter WORKING section; the procedure lives in the injections.
4. Close-out: the ledger-based final report and the claim check.
5. UI: the contract panel (goal, assumptions as chips, items with check status).

## How we'll know

- New long-horizon evals, each with a hidden check suite: a Lisp interpreter (about 200 programs), a 20-chapter
  novella (facts registry and consistency judge), a game in milestones, and a research report with sources.
- Measures per run: hidden checks passing over time, the share of claims the ledger supports, stalls detected and
  resolved, re-injections after summaries, tokens and seconds per passing check.
- Each director rule is checked by ablation: the same tasks with the rule off.
- Haiku 5.5 and Gemini 3.8 Flash, three repeats, against the current harness.

## What the vendors' guides add (read 2026-10-12)

Anthropic: Prompting best practices (Claude 4.5-5.5), Prompting Claude Haiku 5.5, What's new in Haiku 5.5,
Mid-conversation system messages, Context windows. Google: Prompting strategies (2026-09-17), the Gemini 3.8 Flash
model page (2026-10-09), Thinking, Function calling, Long context. Neither publishes a guide specific to Gemini 3.8
Flash beyond its model page.

Changes to the design:

1. **Injections are facts with a reason, not commands.** Both guides warn against emphatic or persuasive wording
   (it causes over-triggering). Write "Item 3's check passed; item 4 is next because …", not "You MUST".
2. **Harness notices sit apart from the user's words.** Anthropic: never put a notice and the user's words in one
   block; Haiku may ignore a notice placed right after a tool result unless it is its own block. Our injections
   are separate `harness` text blocks after the tool results; keep it that way, and never merge relayed user text
   into them. Never edit the system prompt or earlier turns during a run (Haiku 5.5 returns 400 when thinking
   blocks are invalidated).
3. **Tell Haiku about compaction.** Haiku 5.5 doesn't receive the API's context-budget tags, so with a 100k budget
   it can rush to finish. The environment section says that older context is summarized automatically and work
   should continue; the "context near budget" rule says to write Notes, not to wrap up.
4. **Keep-working and real-verification clauses for Haiku.** At low effort with a long prompt Haiku stops early and
   reports changes without checking them. The guide's fixes: "keep working until everything the user asked for is
   done, then stop and report", and "a syntax-only check does not count as verification". The director's
   open-items and claim-check rules enforce both; the prompt states them once.
5. **No blanket search rule.** A rule to search any present-day question made Haiku search half the prompts that
   needed none, with no accuracy gain. Give today's date and the knowledge cutoff instead; round 1's "facts that
   can change come from a tool" is close to the blanket rule and should be watched on the restraint tasks.
6. **Effort, not prompt text, controls thinking.** Haiku 5.5: medium by default (agentic coding), high for strict
   instruction following; low causes early stops and skipped checks. Gemini 3.8 Flash: medium for agents, no
   minimal level, no temperature. The director can raise effort for a step (per-message effort keeps the cache)
   when an item has failed twice.
7. **Gemini: no structured text right before a tool call** (it can end in a malformed function call), short
   prompts, 10-20 tools, and a cap on retries since persistence can loop.
8. **Query last.** Long material first, the instruction at the end: the director's injections already sit at the
   tail.
9. **Explain why.** Each standing rule in the prompt carries its reason in one clause; the models generalize from
   reasons better than from lists.

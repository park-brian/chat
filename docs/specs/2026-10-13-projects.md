# Projects: local folders and git repositories

The user's direction (2026-10-13): let the agent work on local folders, and connect git repositories as projects;
think deeply about getting the harness really working. A `GITHUB_PAT` in `.env` serves evals; users give their
own token in Settings, like the other keys.

## Today

A project is a virtual workspace in IndexedDB: versioned files, run reports, checks. `openFolder` mirrors an
existing app's files to a chosen folder (File System Access API), watches it (FileSystemObserver or a 1.5 s poll)
and lets the disk win on conflicts. It doesn't open a folder as a project (it never imports the folder's own
files), ignores .gitignore, and doesn't know about .git.

## One model: a project has a root

| Root | Source of truth | Read | Write | History |
| --- | --- | --- | --- | --- |
| **Workspace** (today) | IndexedDB | IndexedDB | versions | the harness's versions |
| **Folder** | the folder on disk | the folder (lazily, respecting .gitignore) | to the folder, plus a version in the workspace journal | the folder's own git (isomorphic-git over the directory handle) if there is a `.git`, else the journal |
| **GitHub** | a repository and branch | REST API (tree, blobs) into a cached working copy | the cached copy; `git push` turns commits into Git Data API commits on a branch | the repository's git, plus local commits until pushed |

Everything above the root stays the same: the shell's files, `edit`, `look`, checks, the plan file, versions as an
undo journal. The root decides only where bytes come from and where they go.

### Folder projects

- **Open a folder as a project** (not only mirror an app): import its file list at once, read file contents on
  first access, skip what `.gitignore` and a default list exclude (node_modules, dist, build, .git internals).
- **Two-way sync:** the agent's writes go to disk immediately; the user's edits in their own editor arrive through
  the observer and appear in the next message's `<changes>`. Conflicts: the disk wins, and the agent is told.
- **Permission:** Chrome remembers a granted folder across sessions when the user allows it; on a new session the
  harness asks once with one click. Browsers without the API (Firefox, Safari) get the GitHub and workspace roots.
- **git on the folder:** isomorphic-git through an fs adapter over the directory handle: status, diff, log,
  branch, commit. Push and pull are the user's own (their terminal) or through the local proxy.
- **The shell mounts the folder:** `npm test`, `node`, `python3`, `pytest` run against the user's real project,
  within the shell's limits (no native addons). For a JavaScript or pure-Python project this is the real loop:
  the agent edits the files the user has open, and runs the project's own tests.

### GitHub projects

- **Connect** `owner/repo` and a branch with the user's token (fine-grained, scoped to the repository).
- **Clone** through the REST API (the tree, then blobs on demand) into a cached working copy; record the base
  commit.
- **Work** as in any project; `git status` and `git diff` compare with the base.
- **Push** creates blobs, a tree, a commit on the base, and moves or creates a branch through the Git Data API;
  `gh pr create` (a small shell command) opens a pull request. No proxy needed if the REST endpoints send CORS
  headers (the research checks this).
- **Never push to the default branch** without the user confirming; the default is a new branch per goal.

## Confirmed (research 2026-10-13, curl on the endpoints)

- api.github.com REST and GraphQL send `Access-Control-Allow-Origin: *` and allow Authorization: tree, blobs,
  refs, commits and pull requests all work from a static page with a fine-grained token. Limits: 5,000 requests an
  hour, 80 content creations a minute and 500 an hour (many blob uploads hit this; batch small files as tree entries
  with inline content where the API allows).
- github.com smart-HTTP (isomorphic-git clone and push), codeload tarballs, and OAuth device flow send no CORS
  headers: no git clone against GitHub, no device-flow sign-in, without a relay. The public isomorphic-git CORS
  proxy would see the token: never use it with real tokens.
- Folders: showDirectoryPicker in Chrome and Edge only. Chrome 122+ offers "Allow on every visit" when a stored
  handle is reopened. FileSystemObserver is on by default since Chrome 133 on desktop; on "unknown" or "errored"
  events (missed changes, per-origin limits) the harness re-scans.
- isomorphic-git on a folder: through a thin fs.promises adapter over the directory handle (or ZenFS's WebAccess
  backend, to be checked).

## Why this matters for the harness

It turns goals (docs/specs/2026-10-13-goals-and-primitives.md) into real work: a user's own repository, its own
test suite as the checks, a branch and a pull request as the result. SWE-bench-style tasks on the user's code.

## Experiments

- **E21:** the swe tier run as folder projects (each seed in a temporary folder) and as GitHub projects (a test
  repository): same scores as workspace projects, and what breaks (sync lag, permission, rate limits).
- **E22:** a real repository task end to end (a small open-source JS repo with an issue): goal proposed, tests as
  checks, branch pushed, PR opened against a fork; time, cost, and whether the PR's tests pass in CI.

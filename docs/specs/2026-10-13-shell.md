# A shell for the agent

Why (docs/experiments/LOG.md, E10): with no shell, Haiku spends thinking on how to run tests ("Since I can't execute
node …", 11-16 of 21 swe runs) and falls back to text-presence checks. Cheap models know bash better than any
bespoke tool; current guidance favours CLIs and text-observable feedback. A shell also gives the director one
general check: a command and the exit code it should return.

## Constraints

- Static hosting (GitHub Pages): no response headers, so no COOP/COEP without a service-worker workaround, and no
  SharedArrayBuffer by default.
- Public, open-source app: licenses must allow free public use without a vendor key.
- Cheap models: fast, predictable, and a command set stated up front.
- The workspace (IndexedDB, versioned, with run reports and director checks) stays the source of truth.

## Design

**One tool, `bash`**, following the Anthropic and OpenAI shell tools: input `{ command, timeout? }`; result
`{ stdout, stderr, exitCode, ms }` with a note when output was truncated (first and last parts kept, the full text
saved to a scratch file the model can read). cwd and env persist across calls in the harness (just-bash resets
them per exec). A `restart` resets the session.

**The shell**: just-bash in a dedicated Worker per run, not on the page or in the engine's own thread, so the
harness can `terminate()` it on timeout or Stop. This replaces loop guards for shell code.

**Files**: a just-bash `IFileSystem` over an in-memory copy of the workspace, loaded when the session starts.
After each command the harness takes the changed files and commits them as workspace versions with source
`shell`, so history, diffs, run_app, PLAN.md and director checks see them. Reads are synchronous inside the
worker (Node's `readFileSync` needs that), which the in-memory copy allows without SharedArrayBuffer.

**Commands the harness adds** (just-bash `defineCommand`):

- `node file.js [args]` and `node -e`: runs in a nested Worker with a CommonJS and ESM loader over the same files,
  Node built-ins from a polyfill set (unenv or node-stdlib-browser: path, events, buffer, util, url, stream,
  assert, os stubs), `process` (argv, env, cwd, exit, stdout/stderr writes), `fs` over the in-memory copy.
- `node --test [files]`: the node:test runner from E10 (test/describe/it, hooks, subtests, skip/only), TAP-like
  output and the exit code. The same runner backs run_app on test files.
- `npm install [pkg]`: fetch tarballs from registry.npmjs.org (CORS-open), untar into `node_modules`, write
  package.json and a lockfile; `npm test` and `npm run <script>` run the script through the shell.
  `npx <bin>` runs a package's bin with `node`.
- `curl`/`wget`: through the engine's `proxyFetch`, so the CORS rules and errors are the same as read_url's.
- `git`: isomorphic-git over the same files (init, add, commit, status, diff, log, checkout, branch); clone and push
  only through the local proxy (GitHub sends no CORS headers). Commits can mark milestones.
- `open <file>`: run_app on a page, so the shell can launch what it built.
- `python3 file.py`, `python3 -c`, `pip install <pkg>`, `pytest` (user, 2026-10-13): Pyodide (CPython in WASM)
  in its own Worker, loaded on the first python call (about 10 MB, cached). Its Emscripten file system is filled
  from the in-memory workspace copy before each command and read back after, like node's. `pip` goes through
  micropip: pure-Python wheels from PyPI and the packages Pyodide builds (numpy, pandas and others); packages
  with native code that Pyodide doesn't build fail with a clear message. `pytest` is pure Python and installs
  the same way. This also opens SWE-bench-style tasks on pure-Python repositories.
- **Python as a data and science environment** (user, 2026-10-13). Pyodide builds, loadable with `pip install`
  without native toolchains: numerical (numpy, scipy, mpmath, Bottleneck); data (pandas, polars, xarray,
  narwhals); machine learning (scikit-learn, xgboost, lightgbm); statistics (statsmodels, iminuit,
  boost-histogram); symbolic (sympy, gmpy2); optimization (casadi, nlopt, highspy, clarabel, cvxpy-base);
  visualization (matplotlib, bokeh, altair); images (opencv-python, scikit-image, Pillow, imageio); storage (h5py,
  netcdf4, zarr, pyarrow); databases (duckdb, sqlalchemy); bioinformatics (biopython, pysam, pyrodigal,
  sourmash); population genetics (msprime, tskit, demes); astronomy and physics (astropy, healpy, galpy, rebound,
  reboundx); geospatial (geopandas, shapely, rasterio, Cartopy, pyproj); graphs (networkx, igraph); units (unyt,
  uncertainties).
  - The bash tool's description names these groups in one or two lines: a cheap model won't assume they exist,
    and will otherwise avoid Python or try to build native packages.
  - Figures come back as images: a matplotlib figure saved or shown during a command is returned in the tool
    result, so the model can look at its own chart, the same check-against-reality loop as screenshots.
  - duckdb gives SQL over CSV and Parquet files in the workspace.
  - Not available (no official Pyodide build or not in its package index): PyTorch, TensorFlow, JAX, RDKit,
    Scanpy, OpenMM. The description says so, so the model reaches for what exists (scikit-learn, xgboost and
    lightgbm for models; numpy and scipy for numerics) instead of spending turns on an install that will fail, and
    a failed `pip install` of one of these names says why and what to use instead.
- **Deep learning goes through JavaScript** (user, 2026-10-13). Python in Pyodide has no verified build of
  TensorFlow, PyTorch, JAX or ONNX Runtime and runs on the CPU. The browser has its own implementations, with GPU:

  | Framework | In the browser | GPU |
  | --- | --- | --- |
  | TensorFlow | TensorFlow.js | WebGPU, WebGL |
  | PyTorch | a model exported to ONNX, run with ONNX Runtime Web | WebGPU |
  | JAX | jax-js | WebGPU, WebGL |
  | ONNX Runtime | ONNX Runtime Web | WebGPU, WebNN |
  | NumPy | Pyodide | CPU |

  These run under `node` (its Worker has WebGPU in Chromium) or in the code tool, installed with
  `npm install @tensorflow/tfjs` or `onnxruntime-web`, or imported from a pinned CDN URL. The bash tool's
  description says this in one line ("for neural networks use TensorFlow.js or ONNX Runtime Web from node; Python
  here has no PyTorch, TensorFlow or JAX"), and the failed-install message for torch, tensorflow and jax points
  to it. The spike checks that `navigator.gpu` exists in the node Worker and that a small TensorFlow.js model
  trains there.
  - New eval tasks follow: data questions with exact answers (a regression coefficient with statsmodels, a duckdb
    query over a pinned CSV, a networkx shortest path, a sympy integral), graded mechanically and impossible to
    answer without computing.

**Stated limits**, in the tool description, so the model doesn't plan around tools that aren't there: no native
addons, no Python unless loaded, no `sudo`/package managers other than npm, `child_process` limited to commands
of this shell, network only through the proxy rules.

**Checks**: a new director check kind `command`: `{ kind: "command", run: "node --test", exit: 0 }`, optionally
`stdout` to match. Red-first applies (the command should fail before the work). Most other check kinds can be
written as commands, which keeps the contract to something every model understands.

## What could go wrong

- Node fidelity: tools that need real module resolution, sync `require.resolve`, workers or native code (tsc,
  eslint, jest) may fail. The spike tests them early, and the tool description lists what is known to fail.
- just-bash is beta, and each exec starts fresh: the harness holds cwd and env.
- Bundle size: the shell and polyfills load on the first `bash` call, not at page load.
- Duplicate ways to do things (code tool, run_app, bash): measure which the model uses, and retire what isn't.

## Plan

1. **Spike** (a measured experiment, E11): load just-bash in a Worker in the app; mount the workspace; run a fixed
   command list (ls, grep -rn, sed -i, find, pipes, `node -e`, `node --test` on the swe seeds, `npm install ms`
   then `node -e "require('ms')"`, `git init/commit`). Evaluate almostnode for the node and npm layer against the
   same list. Record what passes, boot time, bundle size.
2. **Build** the `bash` tool, file sync with versions, node/npm/git commands, the `command` check kind.
3. **Measure** (E12): swe, long-lisp and intent with the shell available, against E10's run_app-only version:
   reasoning about running tests, check kinds used, claims matching reports, score, time and cost. Then an
   ablation: shell available, code tool removed, to see whether one general tool beats two specific ones.

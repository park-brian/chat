# A harness that lets the agent see what it is doing

The user's question (2026-10-13): what would I want in a coding harness that lets me see what I'm doing? This is
written from the agent's side. What slows me down when I work is never typing code; it is not knowing what my
change did. Each idea below is something I would reach for, and a hypothesis to test.

## What I would want

1. **A live session, not a fresh process each time.** A Python kernel and a node REPL that keep their variables
   between calls, like a notebook. Today every `code` call starts from nothing, so I re-fetch and re-parse the same
   data. Load a CSV once, then ask ten questions of it.
2. **The difference, not the whole picture.** After a change: what changed on screen (a visual diff of the
   screenshot, with the changed region boxed), in the console (new errors only), in the DOM (nodes added and
   removed), in test results (which flipped). A full screenshot every time makes me find the change myself.
3. **The page as text when that's enough.** The accessibility tree or a compact DOM outline with roles, names and
   positions is often more useful than pixels, and much cheaper. Pixels when the question is visual.
4. **Driving the page.** `look --click "#save" --type "#name=Ada" --wait ".toast"`, then the screenshot, console and
   state. Without it I can't test a flow; I can only look at the first frame.
5. **Tracing without editing.** "Show me every call to `total()` with its arguments and result while I click Save."
   The harness instruments the function for one run and returns the trace, without my adding and removing
   console.logs.
6. **Errors with their source.** An exception shown with the code lines around it and the values of the locals,
   not a stack of file:line references I then have to open.
7. **Which tests cover what I changed.** After an edit to `cart.js:40-55`, run only the tests that touch those lines,
   and tell me which lines no test reaches.
8. **Time travel.** Every version is kept (we have this). Let me run any check against any version, and bisect:
   "the total broke between v12 and v19" found by the harness, not by me reading diffs.
9. **Seeing what the user sees.** Their viewport, the part of the page they scrolled to, what they selected, the
   element they pointed at when they said "this button". Most "it doesn't work" reports are about something
   specific on their screen.
10. **Performance as a number.** Frame time, long tasks, memory, bundle size, measured on every run that matters,
    so "it's slow" becomes "frames take 31 ms, 18 of them in layout".

## What to build first, and how to test it

Ranked by what the evals already show is missing:

- **Driving the page (4)** and **the difference (2)**: game and app tasks lose time on the first frame and on full
  screenshots. Test: game-ambitious and intent-habits, with and without, steps and score.
- **A live session (1)**: research and data tasks re-fetch the same data across calls. Test: research and the data
  tier (to come), calls and tokens per answer.
- **The page as text (3)**: cheaper than screenshots for checks that aren't visual. Test: tokens per run on app
  tasks at the same score.
- **Errors with their source (6)** and **tracing (5)**: swe and long-lisp, steps from first failure to fix.

Each stays inside the primitives (docs/specs/2026-10-13-goals-and-primitives.md): driving, diffs and the text view
are options of `look`; the live session is a mode of `bash` (`python3` and `node` as long-lived kernels); tracing
and coverage are commands in the shell.

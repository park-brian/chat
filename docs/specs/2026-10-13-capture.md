# Seeing a whole page

The problem (user, 2026-10-13): the screenshot tool captures only the visible area, so the model shrinks content to
fit one screen. The tool is shaping the work, which is B3 (tools steer behaviour).

## Options (research 2026-10-13)

| Approach | Renderer | Full page | Status | Limits |
| --- | --- | --- | --- | --- |
| Tab capture (today) | real | no: viewport only | everywhere getDisplayMedia works | needs the user's share prompt |
| Element / Region Capture | real | no: clipped to the viewport by spec | Chrome 132 / 104 | as above |
| **Scroll and stitch** (tab capture) | real | yes | works today; no maintained library | sticky/fixed elements repeat; lazy loading and animation make seams; speed unknown |
| **snapdom** (DOM to SVG foreignObject) | re-rendered | yes, any height (encodes strips past canvas limits) | npm 3.3.3, maintained | cross-origin iframes become placeholders; WebGL needs preserveDrawingBuffer; :hover and form controls approximate |
| HTML-in-Canvas (WICG) | real Chrome painting, readable | likely (to test) | origin trial, ship planned for Chrome 157; API renamed in Sept 2026 | the element must be inside the canvas (clone or render the preview there); cross-origin content omitted |

## Design

`look` gets one option, `full: true`, and chooses the method itself:

1. **HTML-in-Canvas** when it is available (feature-detected), cloning the preview into a drawable canvas.
2. Otherwise **scroll and stitch** if it meets the speed target (below), else **snapdom**.
3. Tab capture stays for "what the user sees right now" and as the fallback.

Scroll and stitch, done carefully:

- pause animations (`document.getAnimations()`), and resume after;
- hide `position: fixed` and `sticky` elements after the first tile so they don't repeat;
- scroll by the viewport height, wait two animation frames and for the tile's images to decode, grab one frame;
- stop at the document's scroll height.

What the model gets: pages, not one tall strip. A page is one or two viewports tall at a resolution where text
stays readable (a 10,000-pixel image is scaled down until it can't be read), labelled "page 2 of 4". The tool's
description says the screenshot captures the viewport and that `full: true` returns the whole page in pages, so
the layout should never be squeezed to fit.

## Experiment (E23)

- **Ground truth:** Playwright's full-page capture (CDP) of the same page in the eval browser.
- **Pages:** a long article, a page with a sticky header and a fixed footer, lazy-loaded images, a canvas game, a
  WebGL scene, a page with CSS animations, a form with focus and hover state.
- **Measures:** time per page and per tile; pixel difference against the ground truth (and where it differs);
  failures (seams, repeated headers, blank canvases).
- **Hypotheses:** scroll and stitch is the most faithful everywhere except seams on animated or lazy pages, at
  50-100 ms a tile; snapdom is faster on long static pages and wrong on WebGL; HTML-in-Canvas (behind the flag) is
  the most faithful where it works.
- **Result (2026-10-13):** docs/experiments/LOG.md, E23. Stitch met the target (75-102 ms a tile) and is the only
  method with a once-drawn WebGL canvas; our snapshot.js (DOM to SVG, no dependency) matched HTML-in-Canvas on
  every page at 2-70 ms and replaced snapdom, which laid 100vh out as the page's height. Built as run_app
  `full: true`: HTML-in-Canvas, else stitch while the tab is shared, else snapshot.js.
- **Then:** whether models stop squeezing content: app and game tasks with `full: true` documented, counting pages
  whose layout was changed to fit one screen (tall content compressed, font sizes dropped, sections cut).

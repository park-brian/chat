# What the model is told, and where

**The goal (user, 2026-10-13): the director has one consistent, controllable way to guide the conversation.**
Everything below serves that:

- **One route.** All steering goes through one function that writes `<additional_instructions>` into the newest
  turn: the director's rules, the old reminders, sub-agent results, the context-budget notice, a new day's date.
  Nothing else in the engine injects text for the model.
- **One format.** Each note is `<instruction rule="same-failure">…</instruction>`, plain and short, a fact with its
  reason; the rule id lets evals count which notes were acted on.
- **One control surface.** The rules table: each rule's condition, text, frequency (once per turn, per event, at
  most every N steps), and priority. At most two notes per step (highest priority first), so a cheap model gets
  one or two clear instructions, not a pile. Every rule can be switched off by flag (`rule.<id>=off`).
- **One log.** Every injection is recorded with rule, step, text and whether it was delivered or capped, and shown
  in the transcript, so a run reads as "the director said X, the model did Y".
- **Metadata stays small.** Steering never travels implicitly in metadata; metadata is the timestamp, the client
  when it changes, this message's attachments and the changes since the last turn.

The user's question (2026-10-13): should per-message metadata carry uploaded files, things created in the
conversation, plan reminders and a goal mode, or should the system message carry that, with metadata kept small
(resolution, mobile or desktop)? This decides where every piece of context lives.

## The two constraints that decide it

1. **The system prompt can't change during a conversation.** It is the cached prefix, and on Haiku 5.5 a changed
   `system` with thinking blocks sent back returns a 400 (Anthropic's Haiku guide). So the system prompt holds only
   what is fixed for the conversation.
2. **Messages can be added but not taken back.** Appending to the newest turn is free for the cache, but every
   block stays in the history, and earlier turns must not be edited. Whatever is sent on every message is paid for
   on every later request: a state snapshot per message grows with turns × state.

So: **fixed things in the system prompt; events and changes in messages; state on request; full state again
only when the history that held it is gone.**

## Channels

| Channel | Carries | When |
| --- | --- | --- |
| System prompt | Persona, rules, tool docs, what the environment offers (shell, packages, network rules), the conversation's start date and the model's cutoff, and the envelope's schema | Once, unchanged |
| `<message><contents>` | The user's words, escaped | Each user message |
| `<metadata>` | The timestamp; the client when it changes (device class, viewport, time zone, locale); this message's attachments (name, type, size, saved path); changes since the last turn (files the user edited, artifacts created or changed, a goal mode switched) | Each user message, usually a few lines |
| `<additional_instructions>` | Director notes, sub-agent results, the context-budget notice | Only when a rule fires |
| Tool results | Their output plus `<metadata>` with start and end times | Each tool result |
| Pulled by tools | The full plan (`plan`), file listings, history, versions | When the model asks |

Full state (goal, items done and open, notes, the files that matter) is pushed again only when the history that
carried it is lost: after a summary, when a goal mode starts, and at milestones. That is when a cheap model needs it
and won't ask.

## The envelope

```
<message><contents>…the user's words, with & and < escaped…</contents></message>        block 1
<metadata>                                                                               block 2
  <timestamp>2026-10-13T14:05:00-04:00</timestamp>
  <client device="mobile" viewport="390x844" />            only when it changed
  <attachments><file path="uploads/q3.csv" type="text/csv" bytes="18234" /></attachments>
  <changes>report.md v3 (the user edited it); chart.png created</changes>
  <goal mode="on" />                                      only when it changed
  <additional_instructions>…</additional_instructions>     only when a rule fired
</metadata>
```

- Two blocks, never one: the Haiku guide says never to put a harness notice and the user's words in one block.
- Everything the harness quotes inside metadata (file names, tool output) is escaped the same way, so nothing a
  user or a web page writes can pass for metadata.
- The system prompt explains it once: metadata comes from the harness, not the user; the timestamp is the user's
  local time; `client` describes their screen (build for it); `additional_instructions` are for the current step,
  not something to repeat in the reply.
- Tool results: `<metadata><started>14:05:02</started><ended>14:05:05</ended></metadata>` inside each result, so
  parallel calls show what overlapped.

## Goal mode

A goal mode ("work on this until it's done") is a setting the user switches, so it is announced in metadata when it
changes, and the director acts on it: the contract starts at once instead of after 8 calls, the full state is pushed
when it starts, the stop rule keeps the run going while items are open, and the run reports progress at
milestones. Turning it off is announced the same way.

## The experiment (E18)

Two versions behind a flag `metadata=minimal|rich`:

- **minimal** (the design above): events and changes only, state pulled, full state after summaries.
- **rich**: the full state (plan, file list, attachments so far) on every user message and after every step.

Hypothesis: minimal matches or beats rich on intent, answer-hard and long, at much lower input cost per turn;
rich may help on long work where a cheap model doesn't call `plan` to read its own state. Measures: scores, input
tokens per request over the run, how often the model calls `plan`/`view_file` to read state, leak count (E6), and
replies that mention metadata nobody asked about.

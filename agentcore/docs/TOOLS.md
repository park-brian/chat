# Tools and connected code: next implementation slice

Status: design, not an implemented feature. The production app currently has one sandboxed Code Interpreter tool. Web Search, Browser, Jira, GitHub, networked code, connection management, and the UI controls below are not yet live. This document is the build contract; do not mark a tool available merely because a CloudFormation resource exists.

## Product decision

Keep **one configured agent per DDB row and one shared Runtime**. Give each agent a short list of capabilities rather than a second harness or a Runtime per integration. The modal agent form becomes the place to enable tools and enter their non-secret options. A separate Connections modal accepts/rotates credentials and binds them to the current user/project; agents reference connection IDs, never secret values.

There are three distinct paths:

| Capability | Execution path | Credential | New persistent resource |
| --- | --- | --- | --- |
| Code workspace | One shared custom AgentCore Code Interpreter, PUBLIC network, executeCode and executeCommand | Only explicit per-agent connection grants; no blanket AWS role | One custom interpreter, possibly one narrowly scoped execution role |
| Web Search | Existing AgentCore Gateway + managed Web Search connector 1.2.0, MCP tools/list and tools/call | Gateway IAM; no external API key | One Gateway target and one narrow Cedar permit |
| Browser | Built-in AgentCore Browser aws.browser.v1, session opened lazily and stopped in finally | No credential by default; authenticated sites need a separate reviewed flow | None if the built-in Browser proves sufficient |
| Jira/GitHub | Code workspace calls native REST/SDKs (and CLI when installed); Runtime only authorizes and vends a selected connection | One owner-scoped AgentCore Identity API-key/OAuth provider per connection | Identity providers plus one metadata row per connection |

Web Search is for searching. Browser is for navigating a known URL and interacting with pages. Do not use a Browser to scrape search engines: it is slower and CAPTCHA-prone. AWS's Web Search connector returns source URLs/snippets and requires us to preserve/display citations. The current plain-text chat view is **not** enough to ship it; add safe citation rendering first. The existing Gateway is default-deny, so creating a target alone must not silently expose it.

“Full access” for Code Interpreter means public network, shell commands, Python/JavaScript/TypeScript, package installation, a writable temporary workspace, background command tasks, and use of explicitly granted API credentials. It does **not** mean an account-administrator IAM role shared with arbitrary generated code. Live probes on 2026-09-23 found `python`, `node`, `curl`, `aws`, `pip`, `npm` and preinstalled `requests`, `httpx`, `boto3`, and `python-dotenv`, but **no git or gh executable**. A disposable custom PUBLIC interpreter reached GitHub HTTPS (200) and installed a pinned Python package from PyPI into `/tmp`; its session was stopped and the resource was confirmed deleted. First use built-in HTTP/SDK capabilities; install a missing library into the current session only when needed. For git/gh, test ordinary installation; if unreliable, stage pinned, checksummed binaries in the existing shared bucket. Do not maintain a custom image or broad dependency set without a measured need. Still benchmark startup and repeated calls under the deployed Runtime role.

### The interpreter as a small, real harness

The Runtime remains the controller and policy boundary; Code Interpreter is the disposable workbench. A model sees a concise, versioned tool contract (`executeCode`, `executeCommand`, `startCommandExecution`/`getTask`/`stopTask`, `readFiles`/`writeFiles`/`listFiles`), the enabled skill guides, and its project context. The Runtime owns the model/tool loop, validates every call, binds a Code Interpreter session to the derived Cognito user + project + chat, streams bounded output as tool events, and observes token/tool budgets. It reuses the same interpreter **resource** for everyone but never a session across users or projects. This is harness-like behavior without another long-running framework, connector wrappers, or one Runtime per agent.

Inside one session the agent can inspect files, write a script, run tests, install a missing package, inspect the failure, and iterate. AgentCore says files and data persist for the session (maximum eight hours) and documents background command tasks. For the first slice, use **one lazy interpreter session per chat request**, shared by all tool calls in that model turn and stopped in the Runtime's `finally` block. This matches current cost/cleanup behavior; it does not promise a persistent workspace across messages. Benchmark this against a 15-minute per-chat lease before adding a DDB session binding, resume/revoke rules, and idle cost. Session state is **not** durable project storage: save only user-selected artifacts to the shared S3 bucket under the owner/project prefix, and reconstruct a future session from Memory, agent config, skills, and those artifacts. Long-running commands must have a task ID, status polling, cancellation, and a bounded wall-clock limit.

The system prompt should favor `requests`/`boto3` and the Python standard library for one-off API work; check `import` or `which` before installation; use `python -m pip install --user` or an isolated session directory only if needed and PUBLIC egress works; avoid printing secrets; show changes/results, not raw credential-bearing command lines; and request confirmation for consequential external writes if the configured approval policy requires it. This is operational guidance, **not** a sandbox or permission boundary. A checked-in skill can teach Jira REST, GitHub REST/GraphQL, or S3 with tiny runnable examples instead of a bespoke adapter for each API.

## One small catalog, not a plugin framework

Add a checked-in `tools.json` only when the first new tool executes. It is an allowlist for UI labels, per-agent options, required connection type, availability, and the tool instructions to show the model. It contains no credentials, dynamic endpoint URLs, executable code, or arbitrary tool schemas copied from AWS. Gateway tools/list remains authoritative for the Web Search invocation schema; the Runtime has explicit handlers for each ID. A proposed v1 shape:

```json
{
  "version": 1,
  "tools": [
    {"id":"code","label":"Code workspace","backend":"code-interpreter",
     "connectionTypes":["github","jira","aws"],"options":{"timeoutSeconds":{"type":"integer","min":60,"max":900}}},
    {"id":"web_search","label":"Web Search","backend":"gateway",
     "connectionTypes":[],"options":{"maxResults":{"type":"integer","min":1,"max":25}}},
    {"id":"browser","label":"Browser","backend":"browser",
     "connectionTypes":[],"options":{"allowedDomains":{"type":"string[]","maxItems":20}}},
    {"id":"github","label":"GitHub","backend":"connection",
     "connectionTypes":["github"],"options":{"repository":{"type":"string"}}},
    {"id":"jira","label":"Jira","backend":"connection",
     "connectionTypes":["jira"],"options":{"projectKey":{"type":"string"}}}
  ]
}
```

The agent row stores only `toolsJson` and a revision, for example `{"code":{"enabled":true,"connectionIds":["..."]},"web_search":{"enabled":true,"maxResults":5},"browser":{"enabled":false}}`. The Runtime checks every ID/option against the catalog and verifies each referenced connection belongs to the derived Cognito subject/project. Unknown IDs, unavailable infrastructure, incompatible model adapters, and ungranted connections are rejected server-side. Do not let a browser-supplied tool schema, URL, secret ARN, actor ID, or IAM role become authoritative. Keep any provider-specific execution switch visible in `controller.js`; the JSON is metadata, not a code-loading system.

Code instructions should be short, checked-in, and loaded only for granted tools: e.g. `docs/tool-guides/github.md` documents `requests`/`gh api`/`git` patterns; Jira documents REST base URL, auth mode, pagination, and safe issue changes. They refer to environment variable **names**, not values. Version the guide with the catalog so an agent can learn how to use native SDKs without adding a JavaScript wrapper for every provider. Never claim the instructions enforce permissions; the credential and Runtime grant do.

## UI shape

The existing Agents dialog gains a “Tools” section with five compact rows. Each row has an enable switch, availability/status text, and an inline “Configure” expander containing only its relevant inputs:

- Code workspace: PUBLIC-network warning, maximum run time, read/write connection grants. A full-access grant is explicit because generated code can read and transmit any key placed in its session. Show the exact granted connections before saving.
- Web Search: enable, max results, and administrator-controlled domain policy shown read-only; date/domain filters for individual calls stay model inputs. Show a citation indicator in the chat transcript.
- Browser: enable, allowed domains/start URL, max actions/session duration, and whether screenshots/live view are allowed. Browser session controls appear in a tool activity panel, not as another chat page.
- GitHub: choose a saved connection, default owner/repo/branch, read-only or write-capable intent, and “Test connection.” Do not suggest that an intent toggle can narrow a write-capable PAT inside unrestricted code.
- Jira: choose a saved connection, site URL/project key, read-only or write-capable intent, auth mode (Cloud email+API token vs bearer token), and “Test connection.”

The Connections dialog lists `provider, scope, display name, owner/project, status, testedAt, grants` and offers Add, Rotate, Test, Revoke. A key input is write-only: never reveal it on read or return it in a list response. Show a clear separate “Grant to full-access code” action. Admin can set account availability/default policy; a normal user can manage only owned connections and agents. An account-level shared key needs explicit per-user/project grants; tags help inventory, not authorization. Do not put tools in a generic admin model table.

## Minimal Runtime API and data

Keep the single `POST /invocations` contract. Add only:

| Command | Permission | Result |
| --- | --- | --- |
| `tools.list({projectId})` | signed-in | Catalog plus actual stack/model capability flags and owned connection status; no secret |
| `connections.list({projectId,cursor})` | owner/admin inventory | Metadata pages, never credential body |
| `connections.put({projectId,type,displayName,siteUrl?,authMode?,accountEmail?,secret})` | owner | Validate provider-specific fields, create/rotate one AgentCore Identity provider, save metadata row, return ID/status only |
| `connections.test({projectId,id})` | owner | One bounded read-only GitHub/Jira identity API call through the Runtime; record status/time |
| `connections.revoke({projectId,id})` | owner | Deny new grants first, then delete provider and metadata with on-demand cleanup for a partial failure |
| `agents.put({...,tools,revision?})` | owner | Validate catalog, model compatibility, and owned connection grants; revisioned edit/create |

Connection metadata is one row in the existing table under `PROJECT#sub/project` with `CONNECTION#id`, type/site/display/status/providerName/createdAt/revision and optional explicit grants. Provider names/tags include `app`, `stack`, `owner-sub`, `project`, `connection-id`. The secret lives only in AgentCore Identity's managed provider (or an external Secrets Manager secret referenced by it), not DynamoDB, Memory, S3, agent config, usage, or the GitHub Pages URL. Account-wide defaults remain one control row. No new table or per-user stack.

Use `.env` for **local tests and explicit bootstrap only**: `GITHUB_PAT`, `JIRA_API_KEY`, and `JIRA_URL` already exist; `JIRA_EMAIL` is not present, so do not assume Jira Cloud Basic auth. The smoke setup may create temporary Identity providers with those values and remove them in `finally`. If the owner later wants a permanent connection, create it through the authenticated Connections UI and associate it with the chosen Cognito user/project. No `.env` value belongs in source control, CloudFormation outputs, CodeZip environment variables, browser storage, or test logs.

## Credential boundary for full-access code

Code is the **primary** Jira/GitHub integration path: one Code Interpreter tool, small provider-specific guides, and a selected connection. The Runtime is only a credential/authorization broker plus a bounded read-only connection test, not a growing library of Jira/GitHub operations. Use Gateway for native Web Search and later only where its schema/policy materially helps. The Jira integration-provider template is currently console-only and requires hosting an external server, so it is not a no-code native Jira connector.

The user's local `.env` does **not** automatically appear in an AgentCore Code Interpreter session. Nor do the Runtime's environment variables: the Code Interpreter `StartCodeInterpreterSession` API has no environment-variable field. For each chat session, the Runtime derives owner/project, checks the current agent's connection IDs and grants, fetches only those secrets with its user-bound AgentCore Identity token, and writes **one session-local `.env` file** through Code Interpreter `writeFiles` before any model-generated code runs. It must contain only this session's non-secret context and explicitly granted connection values. Target a documented contract such as `GITHUB_TOKEN`, `JIRA_URL`, `JIRA_EMAIL`, `JIRA_API_TOKEN`, and optional AWS temporary credential variable names. The prompt contains names and connection labels, not the initialization payload; generated code can nevertheless read the file, as intended by a full-access grant. Neither the browser nor agent config sends a secret in a chat prompt.

Live dummy-value tests establish the loading rule: `writeFiles` accepts a relative `.env` path (it rejects an absolute path); shell/Python run in the shared workspace, but Node `executeCode` has a different working directory. First resolve the file's absolute path with a non-secret `pwd`/Python probe and retain it in the Runtime's session state. Prefix **every** `executeCommand` and background command with `set -a; . "$ENV_PATH"; set +a;`; shell exports do not persist across calls. Prefix Python `executeCode` with `load_dotenv(ENV_PATH, override=True)`; Python-set variables did persist in the live session, but reloading makes rotation predictable. For JavaScript/TypeScript `executeCode`, request `runtime: "nodejs"` explicitly and load the absolute path (Node's `process.loadEnvFile` worked); the default Deno runtime denied environment access in the probe. Do not embed secret literals in generated command/code arguments, display the file contents, or rely on filesystem mode bits as isolation. Refreshing a grant should stop/recreate the session and `.env` instead of modifying credentials underneath running code.

Because PUBLIC code can read and transmit anything in its session, an explicit “grant to code” means **that agent may exercise the credential's full external scope**, including writes. A UI read-only intent cannot narrow a write-capable PAT. Prefer repo-scoped fine-grained GitHub PATs or short-lived GitHub App tokens and narrowly scoped Jira identities. Never give the interpreter an IAM role that can enumerate/read every user's Identity providers or Secrets Manager secrets. The first slice stops the session in `finally`; if a later per-chat lease is added, revocation must stop every leased session containing that grant. Enforce owner/project binding on every tool call. Verify experimentally whether initialization payloads, command arguments, process listings, CloudTrail, and logs can expose a secret before shipping this path. Redact exact key strings from accidental output, but arbitrary code can deliberately encode/exfiltrate them, so redaction is not a security boundary. If safe transport cannot be verified, disable credentialed code and offer only bounded Runtime-side connection tests until it can.

For a customer's AWS account, favor a customer-created, scoped cross-account role over static AWS keys. The Runtime validates the saved role connection, assumes it with an external ID and short duration/session policy, then vends those **temporary** credentials only to that owner's Code Interpreter session. A customer may choose a broad role, but the UI must show its effective authority and never silently borrow the app administrator's `eaap` profile. The shared interpreter execution role itself stays minimal (ideally no customer-resource access); otherwise every user's generated code can access its MMDS credentials. If a narrow app-owned S3 artifact permission is needed, mediate it through the Runtime or verify a per-user isolation mechanism rather than giving the shared role access to all prefixes.

## Model/tool execution and usage

Bedrock Converse can advertise enabled tools and feed validated results back into its existing eight-turn loop. Gemini currently supports **text only** in this app; do not enable tools for it until a function-call adapter preserves Gemini 3.x thought signatures/call IDs and returns function responses correctly. The agent form and Runtime must agree on that capability. Each tool result is bounded in size and has an observed `tool.done` event; do not store search-result bodies, browser screenshots, API keys, terminal history, or raw third-party responses in Memory. Save only necessary citations/links and conversation text.

Each web search, browser action/session, code invocation, and Jira/GitHub operation gets its own usage row with request/tool ID, UTC time, owner, duration, status, resource units, price source/quality, and no secret or sensitive response. Until a current official price and meter are verified, mark it `unpriced` and keep budget enforcement explicitly model-only/partial. Use one lazy tool session per request initially, cap turns/actions/duration, and stop it even on model or browser failure. A background browser job is not needed for the first slice; long tasks follow the existing durable on-demand task design.

## Implementation sequence and live gates

1. **Catalog and UI skeleton.** Add `tools.json`, one tool section in the Agents dialog, provider-aware enablement, server validation and revisioned agent edit. Generic `tests.js` stories verify labels/options, unauthorized connection IDs, incompatible Gemini tools, mobile layout, and no secret persistence. No AWS resource should be created merely by opening a modal.
2. **Full-access Code Interpreter.** Replace the system sandbox route with one shared CloudFormation `AWS::BedrockAgentCore::CodeInterpreterCustom` in `PUBLIC` mode. The disposable direct-API probe already verified outbound HTTPS and pip installation; now test under the deployed Runtime role, measure startup/warm latency, test `git`/`gh` installation, background tasks and no cross-session state. Keep execution IAM minimal. Expose `executeCommand`, file and background-task operations alongside `executeCode`; implement the harness instructions and explicit UI warning. Create a session-local `.env` via `writeFiles` even without connected secrets, and test shell/Python/Node loading with dummy values. Verify teardown.
3. **Web Search.** Add a CloudFormation GatewayTarget for connector `web-search` pinned to `1.2.0`, Gateway role permissions `InvokeGateway`/`InvokeWebSearch`, Runtime `InvokeGateway`, and a narrow reviewed Cedar permit. Exercise tools/list and one real search through the Runtime; test default-deny, domain filtering, citations, and tool usage row. Add safe citation rendering before exposing search to users.
4. **Managed Browser.** Probe built-in `aws.browser.v1` in a disposable stack/session; use its SDK session APIs plus CDP or InvokeBrowser as appropriate. Implement navigate/snapshot/click/type/screenshot with bounded outputs, allowlist checks, and guaranteed stop. Test a public deterministic page and inspect desktop/mobile tool activity; do not use a search engine as the test.
5. **Connections and native APIs.** Add Identity-backed user/project connections and read-only GitHub `GET /user`/repo and Jira `myself`/project smoke using the `.env` test keys. Determine Jira auth mode from a live read-only call; do not guess. Test cross-user denial, key rotation/revocation, rate limits, and failure cleanup. Introduce write operations only with temporary test resources and cleanup.
6. **Credentialed code.** After the secret-transport audit, grant selected connections to one interpreter session and test read-only `requests`/`boto3`/`curl` calls, then optional `gh api`/`git`. Test a temporary customer-style scoped AWS role with `GetCallerIdentity`, one allowed S3 action, and one denied action; remove all resources. Exercise exfiltration/redaction, cross-user isolation, and disabled/revoked-connection behavior. If the audit fails, keep credentialed code disabled and document the limit honestly.
7. **Provider parity and costs.** Add Gemini tool-call support with thought-signature replay, then price/quality reconciliation for Gateway, Browser and Code Interpreter. Benchmark first tool use and warm repeated calls against the current ~500 ms Runtime path; add no worker/resource without a measured need.

Reuse one named disposable CloudFormation stack and real AWS services during development. Scripted echo may control the model's tool requests; do not mock Gateway, Browser, Identity, Code Interpreter, Jira, or GitHub. Tests must track every temporary provider, session, Cognito user, Memory event, table row, and object and remove them in `finally`. After the last live story, delete the exact stack and retained bucket only after tag/content checks. Keep the published URL at `https://park-brian.github.io/chat/agentcore/`.
